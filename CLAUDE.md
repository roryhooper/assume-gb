# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ASSUME is an agent-based electricity market simulation framework (published on PyPI as `assume-framework`) with optional deep reinforcement learning for bidding agents. It is built on the `mango-agents` multi-agent framework.

## Commands

```bash
# Dev install (on machines without a GPU, install CPU torch first to avoid the multi-GB CUDA build)
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -e ".[all]"
pre-commit install

# Lint/format (ruff with --fix, ruff-format, codespell, REUSE license headers, whitespace fixers)
pre-commit run --all-files

# Tests (testpaths=tests, asyncio_mode=auto)
pytest
pytest tests/test_powerplant.py
pytest tests/test_powerplant.py::test_init_function
pytest -m "not slow"

# CI runs the suite in three stages as optional extras are added:
pytest -m "not require_learning and not require_network"   # core only
pytest -m "require_network and not require_learning"       # needs [network] (pypsa)
pytest -m "require_learning"                               # needs [learning] (torch)

# Run an example simulation (pick an entry from available_examples in examples/examples.py)
python examples/examples.py
assume -s example_01a -c base -db "sqlite:///./examples/local_db/assume_db.db"   # CLI, see `assume -h`

# Docs
pip install -e .[docs]   # also needs pandoc on the system
python -m sphinx docs/source docs/build
```

Optional extras gate features: `learning` (torch: RL strategies, MATD3), `network` (pypsa: redispatch, nodal/zonal clearing), `oeds` (OEDS scenario loader). Registries import these in `try/except ImportError`, so missing extras silently drop the corresponding strategies/mechanisms rather than failing.

## Repository conventions

- New data files (e.g. CSVs in `examples/inputs/`) need a sibling `.license` file; the pre-commit REUSE hook only annotates source files.
- `docs/source/` is the source of https://assume.readthedocs.io. Its hand-written `.rst` pages (e.g. `market_config.rst`, `units.rst`, `demand_side_agent.rst`, `learning.rst`) are the reference for config options and concepts; read them locally rather than fetching the site. The `docs/source/assume*.rst` API pages are generated by `sphinx-apidoc -o docs/source -Fa assume`, so don't edit them by hand.
- User-facing changes are recorded in `docs/source/release_notes.rst` (the PR template asks for this, plus docs updates and tests).
- Python 3.11–3.14 are tested in CI. Pandas is pinned to `>=3.0,<3.1`.

## Architecture

### Simulation runtime (`assume/world.py`)
`World` is the central container. It creates a mango container, then registers:
- **Market operators** (`add_market_operator`) holding one or more **markets** (`add_market`), each a `MarketRole` subclass chosen by `MarketConfig.market_mechanism` from the `clearing_mechanisms` registry.
- **Unit operators** (`add_unit_operator`), each a `UnitsOperator` role (`assume/common/units_operator.py`) managing a portfolio of units.
- **Units** (`add_unit`), instantiated from the `unit_types` registry with one bidding strategy per market (`bidding_strategies` dict keyed by market id).
- An **output agent** (`assume/common/outputs.py`) that writes to a SQL DB (TimescaleDB/Postgres or SQLite) and/or CSV.

`World.run()` drives an `ExternalClock` step-by-step (simulated time, not wall time); a real-time mode and a distributed manager/worker mode (`distributed_role`) also exist. Because it calls `nest_asyncio2.apply()`, it works inside Jupyter.

### Message flow per market round
Agents communicate only via mango messages (`assume/common/market_objects.py` defines `MarketConfig`, `MarketProduct`, `Order`/`Orderbook` and the message TypedDicts):
1. `MarketRole.opening()` broadcasts an opening to registered unit operators.
2. `UnitsOperator.submit_bids()` asks each unit's strategy for bids (`BaseStrategy.calculate_bids(unit, market_config, product_tuples)`) and sends the orderbook.
3. `MarketRole.clear_market()` calls the mechanism's `clear(orderbook, market_products)` and returns accepted orders/market meta.
4. `UnitsOperator.handle_market_feedback()` sets unit dispatch (`set_dispatch_plan`), computes cashflow and (for learning strategies) rewards, and writes outputs.

### Plug-in registries (string name → class)
New units, strategies or market mechanisms must be registered here to be usable from configs:
- `assume/units/__init__.py` → `unit_types`; DSM sub-components in `assume/units/dst_components.py` → `demand_side_technologies`.
- `assume/strategies/__init__.py` → `bidding_strategies` (naming pattern `<unit>_<product>_<method>`, e.g. `powerplant_energy_heuristic_flexable`) plus `deprecated_bidding_strategies` for old names, which World merges in.
- `assume/markets/clearing_algorithms/__init__.py` → `clearing_mechanisms`.

### Units and strategies
- `assume/common/base.py` holds the core abstractions: `BaseUnit`, `SupportsMinMax` (generators/demands), `SupportsMinMaxCharge` (storage), `BaseStrategy`, `LearningStrategy`, and `LearningConfig`.
- Units hold time series as `FastSeries`/`FastIndex` (`assume/common/fast_pandas/`), a NumPy-backed, partially pandas-compatible replacement for `pd.Series` used for speed. Indexing semantics (`.loc`, `.at`, `.iloc`) mimic pandas but are a separate implementation; check `tests/test_fast_pandas_*.py` when changing behavior.
- Each unit has a forecaster (`assume/common/forecaster.py`, with pluggable algorithms in `forecast_algorithms.py`) providing prices, availability, fuel prices etc.
- Demand-side management units (`building`, `steel_plant`, `cement_plant`, `hydrogen_plant`, `steam_plant`) build Pyomo optimization models from `dst_components` and share flexibility logic in `dsm_load_shift.py`. They support full-horizon and rolling-horizon optimisation. The solver is picked by `get_supported_solver_pyomo()` in `assume/common/utils.py`; `highspy` is installed as a core dependency.
- Some market mechanisms also use Pyomo (`complex_clearing`) or PyPSA (`redispatch`, `nodal_clearing`; helpers in `assume/common/grid_utils.py`).

### Reinforcement learning (`assume/reinforcement_learning/`)
`LearningRole` (`learning_role.py`) is attached to the world when `learning_mode` is enabled; it owns the replay buffer and the algorithm (MATD3 in `algorithms/matd3.py`, actor/critic networks in `neural_network_architecture.py`). Learning strategies live in `assume/strategies/learning_strategies.py` and `portfolio_learning_strategies.py`. Training is orchestrated episodically by `run_learning()` in `assume/scenario/loader_csv.py` (training episodes, periodic evaluation, early stopping, then a final run with the trained policy). Metrics go to TensorBoard (`tensorboard --logdir tensorboard`).

### Scenarios (`assume/scenario/`)
- `loader_csv.py` is the main entry: `load_scenario_folder(world, inputs_path, scenario, study_case)` reads `examples/inputs/<scenario>/config.yaml`, where each top-level key is a study case with `start_date`, `end_date`, `markets_config`, learning settings, etc. Unit data comes from CSVs in the same folder (`powerplant_units.csv`, `demand_units.csv`, `storage_units.csv`, `exchange_units.csv`, time series like `demand_df.csv`, `fuel_prices_df.csv`, optional grid files). `yaml_include.py` adds `!include` support to configs.
- Alternative loaders exist for AMIRIS, OEDS and PyPSA scenarios.
- The CLI (`assume_cli/cli.py`, entry point `assume`) wraps the CSV loader: `-s` scenario, `-c` study case, `-db`, `-csv`, `-i` inputs path.

### Results infrastructure
`docker compose up -d` starts TimescaleDB (`postgresql://assume:assume@localhost:5432/assume`) and Grafana with preconfigured dashboards at `http://localhost:3000` (configs in `docker_configs/`).
